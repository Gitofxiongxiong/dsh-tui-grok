# v0.2.0 发布恢复工作流

## 目标

- 修复 `release.yml` runtime bootstrap integrity 分支的 shell heredoc 解析错误。
- 保持已推送的 `v0.2.0` Tag 与已发布的 npm `0.2.0` versions 不变。
- 让正式 workflow 可以从 `main` 显式指定不可变 release Tag，并从该 Tag checkout、重建和校验候选。
- 让 native、runtime 与 CLI 发布步骤可安全重入：版本已存在时只核对同一 tarball integrity 与 `release-candidate`，不存在时才通过 OIDC publish。

## 背景与证据

- 不可变 Tag：`v0.2.0`，commit `77ae309f8df2547f628b26c62414885349d7fa1c`。
- Tag artifact run：GitHub Actions `33308926704`，五平台 native 与 JS candidates 全绿，publish jobs 按设计跳过。
- 正式 workflow run：GitHub Actions `33309459911`。
- 五个平台 native 已通过 OIDC 发布到 `release-candidate`；runtime 首包已由 Tag artifact bootstrap，并已验证 registry integrity 与 Tag tarball SHA-512 一致。
- `publish-runtime` 在执行 integrity 分支前因 heredoc closing marker 被 workflow indentation 破坏而 exit 2；registry cold/PTY、CLI publish 与最终 registry gate 均未执行。
- runtime 是 registry 首个/唯一版本，npm 自动建立 `latest=0.2.0`，且 registry 对删除唯一版本默认 tag 返回 400；保留该事实并在最终记录中说明。

## 设计契约

- 不移动、删除或重建 `v0.2.0` Tag；不覆盖、unpublish 或复用任何已发布 npm version。
- recovery dispatch 必须同时提供 `release_tag=v0.2.0`、
  `resume_run_id=33309459911` 与 `confirm=publish-v0.2.0`。
- workflow definition 可来自 `main`，但所有 package build/cold rehearsal checkout 必须精确使用 metadata 解析出的不可变 Tag。
- recovery 必须核对来源 run 的 `head_sha`、Tag、workflow path、event 与完成状态，并复用该 run 实际发布时保存的 native/JS artifacts。不得以新的 native rebuild 代替来源制品：两次候选对比显示 Linux、macOS、runtime 与 CLI 字节级一致，但 Windows native tarball SHA-512 不同。
- 已存在的 package version 必须将 registry `dist.integrity` 与来源 run tarball 的 SHA-512 比较，并确认 `release-candidate` 指向精确版本；任何不一致立即失败。
- CLI 仍只能在 registry cold/warm/offline、doctor/smoke 与 PTY 全绿后发布。
- 其余包的 `latest` 与 GitHub Release 在最终 registry/provenance 门禁通过前保持不变。

## 风险

- recovery workflow 若未 checkout Tag，可能把 Tag 之后的源码装入 `0.2.0` tarball。
- 重入判断若只检查 version、不检查 integrity，可能静默接受不同制品。
- GitHub workflow expression、跨平台 bash 或 npm view 输出差异可能导致恢复链再次停止。
- npm 新包的自动 `latest` 行为造成 runtime 在统一提升前短暂/持续可见；不得据此提前提升其他包。

## 回滚方式

- PR 合并前直接关闭 PR，不影响不可变 Tag 与现有 registry versions。
- recovery run 失败时继续保留所有已发布版本及现有 dist-tags，停止 CLI publish、统一 `latest` 与 GitHub Release。
- 不 force-push Tag、不 unpublish；若证实 tarball 有内容缺陷，再按新 patch version 发布并 deprecate 有问题版本。

### 实现摘要

- 修复 runtime integrity 分支的 heredoc 解析错误，改为无 heredoc 的 Node SHA-512
  计算。
- `workflow_dispatch` 新增必填 `release_tag` 与可选 `resume_run_id`；metadata 从完整
  Git history 解析 Tag commit，checkout detached Tag 后核对八个 manifest versions。
- recovery 来源 run 必须同时满足：`head_sha` 等于 Tag commit、`head_branch` 等于 Tag、
  workflow path 为 `.github/workflows/release.yml`、event 为 `workflow_dispatch`、status
  为 `completed`。
- 正常 run 仍从 Tag 构建；recovery run 从来源 run 下载五个平台 native 与 JS candidates，
  再作为当前 run artifacts 传递给后续 jobs。
- native、runtime 与 CLI 全部支持安全重入：registry version 已存在时校验 tarball
  SHA-512 integrity 和 `release-candidate`，E404 时才 publish。
- registry cold job 始终 checkout metadata 指定的 Tag；CLI 仍位于 cold/warm/offline、
  doctor/smoke 与 PTY 之后。
- 发布规范与 checklist 已同步默认分支 dispatch、显式 Tag、来源 run artifacts 与
  纯编排故障恢复边界。

### 发现与处置

  integrity match 且 `release-candidate=0.2.0`；CLI `0.2.0` 仍为 E404，符合后续 OIDC
