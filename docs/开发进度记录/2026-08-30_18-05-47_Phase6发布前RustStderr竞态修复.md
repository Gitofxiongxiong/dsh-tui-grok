# Phase 6 发布前 Rust stderr 竞态修复

> 记录时间：2026-08-30 18:05:47 +0800
> 操作者/agent：Codex
> 状态：completed

## 目标与背景

- PR #4 CI run `33305533333` 的 Ubuntu Rust job `99241309560` 在
  `stderr_flood_is_drained_and_does_not_deadlock_hello` 失败；macOS 同一
  `cargo test` 已通过。
- 失败时 hello 正常返回，stderr tail 已达有界上限 `32768` 字节，
  但测试立即取样时末尾 `STDERR_FLOOD_DONE` 尚未被后台 drain 线程纳入。
- 产品实现本来就使 stdout RPC reader 与 stderr drain 线程并行；子进程的
  写入顺序不保证父进程两个读线程的调度顺序。

## 计划修改范围

- 只修改 `crates/dsh-pager/tests/spawn_contract.rs`：hello 返回后以有界
  deadline 等待 stderr 末尾标记，然后执行原断言。
- 不修改 transport 生产代码、Rust wire 语义、协议版本或 UI。

## 风险与回滚

- deadline 必须保持有界，不能把真正的 drain 死锁变成无限等待。
- hello 的五秒延迟断言保留，末尾标记断言保留；本批可单独 revert。
- PR 全矩阵通过前不合并，不执行 npm publish/dist-tag、Tag 或 Release。

- `cargo fmt --all -- --check` 与 `git diff --check` 通过。

## 实际修改与验证结果

- GitHub job log 显示，失败时 `384/384` textarea 测试、`89/89`
  pager unit tests 以及其他 integration tests 已通过；唯一失败是在
  hello 成功后立即取样 stderr tail，得到恰好 `32768` 字节但尚无
  `STDERR_FLOOD_DONE`。
- 修改仅在 hello 延迟断言之后增加最长两秒、每 10ms 轮询一次
  的 tail drain 等待；deadline 到达后仍执行原末尾标记断言。
- 修改前目标测试在本机连续 100 次均通过，与 CI 的低概率调度竞态
  特征一致；修改后再连续执行 100 次，`100/100` 通过。
- `cargo test --workspace --all-targets`：通过，全 workspace 无失败。
- `cargo fmt --all -- --check`：通过。
- `git diff --check`：通过。
- 本批未修改生产代码，未执行 npm publish/dist-tag、Git tag/Release 或
  PR merge。
