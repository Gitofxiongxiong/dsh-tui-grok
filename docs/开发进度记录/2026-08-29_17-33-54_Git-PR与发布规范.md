## 目标与背景

为仓库增加一套可直接执行的 Git 分支、push、Pull Request、合并和
Tag/npm 发布规范，解决“日常 main push 与公网发包耦合”的风险。
规范需同时反映当前 GitHub Actions 的真实触发条件，并给出 `git` 与
`gh` 命令行的标准操作路径。

## 设计契约和复用依据

- 对应长期计划章节：`GROK_BUILD_TUI_DEEPSEEK_ADAPTATION_PLAN.md` 2.8、2.9、M10、M11。
- 对应发布设计：`PRODUCT_PLUGIN_LAUNCHER.md` 的 v2 发布单元、顺序和 Trusted Publishing 契约。
- Grok source path、commit、SOURCE_REV：不适用；本批次只修改仓库治理文档。
- 复用等级：D（GitHub/发布治理，不属于 Grok UI 源码复用）。
- 保持“一份主进度记录对应一个 commit”；默认用 rebase merge 保留
  PR 中每个 commit 与记录的一对一关系。

## 风险、回滚和依赖

- 风险：规范超前于现有 workflow，使用者误以为 Tag 已能完整发布所有包。
  处置：单列“当前实现”和“目标政策”，把不一致项标为阻塞。
- 风险：squash 合并破坏进度记录/commit 一对一。处置：默认 rebase merge；
  只有将 PR 收敛为单一记录时才允许 squash。
- 风险：当前工作区有其他未提交改动。处置：只修改和暂存本记录列出的
  3 个文档文件。
- 回滚：回退本批次的文档 commit；不需要更改代码或外部发布状态。
- 依赖：GitHub CLI 用于 PR 命令；纯 Git 只负责本地分支、commit、push 和 Tag。
