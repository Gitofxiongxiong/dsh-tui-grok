## 目标与背景

- 用户明确授权直接发布一个新版本，真实验证刚合入 `main` 的 npm 目标 tag 和
  GitHub Release 自动化。
- npm 七个公开包当前最高版本与 `latest` 都是 `0.2.1`，GitHub Latest Release 是
  `v0.2.1`；已发布版本不可覆盖，因此本次准备 stable patch `0.2.2`。
- 本版本不新增产品行为；发布内容是已在 `main` 通过 CI 的 `0.2.1` 后续发布编排
  自动化，并保留无参数默认新建对话和 DSH `0.1.1-rc.2` 精确 backend 契约。

## 设计契约和复用依据

- 对应流程：`docs/GIT_PR_RELEASE_WORKFLOW.md` §7 与
  `docs/RELEASE_CANDIDATE_CHECKLIST.md`。
- 复用 `v0.2.1` 发布范围：Cargo workspace、根 npm manifest、11 个 workspace package
  manifest 和两个 lockfile 统一到 `0.2.2`；CLI 的五个 native 精确依赖以及 TUI
  server 的 protocol 精确依赖同步。
- 发布 source 必须是 release PR 经 CI 合入后的远程 `main` 单一 commit；只在该 commit
  上创建 annotated `v0.2.2` Tag。
- Tag push 只构建 immutable candidates；候选 run 全绿后才从 `main` dispatch
  `release.yml`，输入 `release_tag=v0.2.2` 和 `confirm=publish-v0.2.2`。
- stable 版本必须由 workflow 通过现有 Trusted Publishing/OIDC 直接发布到 `latest`；顺序
  为五个 native → runtime → candidate registry rehearsal → CLI → registry/provenance 核验 →
  official CLI rehearsal → 自动 GitHub Latest Release。
- 正常首次 run 不使用 `resume_run_id`；只有内容不变且 integrity 完全一致的部分
  发布纯编排故障才允许恢复。

## 风险、回滚和依赖

- Tag 前失败：修正 release branch/PR，不产生 registry 副作。
- Tag 后、publish 前失败：保留不可变 Tag，停止发布并评估新 patch；不重定位远程 Tag。
- 部分 package 已公开：不覆盖、不重用版本。只有纯编排失败且来源 artifact integrity
  完全匹配时才使用 recovery dispatch；内容缺陷改发新 patch。
- native/runtime 的 `latest` 会早于 CLI 移动，但旧 CLI 使用精确旧依赖；CLI 仍最后
  publish，且有发布前后两轮 registry rehearsal。
- workflow 依赖 GitHub `npm-release` environment 和七个包已存在的 Trusted Publisher。如出现
  GitHub/npm 人工审批或浏览器验证，立即通知用户，不改用本地长期 token。
- 回滚：Tag 前可通过新提交修正本分支；Tag 后不删除公开版本，按发布故障流程
  记录、deprecate/显式 tag 调整或新 patch。
