# Playwright 诊断运行态组件消失

> 记录时间：2026-08-29 15:46:15 +0800
> 操作者/agent：Codex
> 状态：completed

## 目标与背景

用户报告完整滚动状态闭包接入后，流式输出期间输入框上方的 Thinking/Responding
Turn Status 和 reasoning item 的运行态行波不可见。本批使用真实
`ttyd + xterm.js + Playwright` 渲染链路复现，并补充不含 prompt、reasoning 或
response 正文的可开关诊断日志，确定问题发生在 DSH 运行态投影、Grok
scrollback materialization，还是最终 xterm.js 像素输出。

## 风险、回滚和依赖

- 日志若逐帧写盘会影响动画，因此按状态指纹去重，且仅在显式设置
  `DSH_PAGER_DIAG` 时启用。
- mock 事件间隔必须足够长，使 Playwright 能截到 reasoning 和 responding 两个
  运行态；结束时清理 timer，避免测试子进程残留。
- 回滚方式：删除新增日志字段/调用和 mock 场景；临时 `/tmp` 工件可直接丢弃。
- 依赖本机 `ttyd`、Playwright Chromium、当前 debug binary；统一使用 1200×800、
  DPR 1、DejaVu Sans Mono 16px、`TERM=xterm-256color`。

## 实际修改

- `crates/dsh-pager-grok-ui/src/runtime.rs`
  - 在既有 `DSH_PAGER_DIAG` 开关内记录启动时的 `NO_COLOR`/`TERM_PROGRAM`；
  - 增加去重后的 `turn-chrome` 状态指纹：只含 session running、visible、activity
    variant、pending input 和布局矩形；
  - 增加去重后的 `transcript-chrome` 状态指纹：只含 running entry/reasoning
    entry/animated visible line 计数、pane animation、follow 和 viewport 几何；
  - 不记录 prompt、reasoning、response、tool 参数或文件内容，不改变任何可见性和动画
    判断。
- `crates/dsh-pager-bin/tests/mock-server.mjs`
  - 增加 `chrome stream smoke` 的确定性真实协议夹具，按
    reasoning → responding → completed 生命周期发送事件；
  - 增加可选 `DSH_MOCK_DIAG`，只记录事件 seq/type/chunk type 和 running 状态，
    不记录正文。
- 临时 Playwright driver 和证据均位于 `/tmp`，未进入仓库。

  - `cargo fmt --all -- --check`：通过；

  - `cargo build -p dsh-pager-bin`：通过；
  - `git diff --check`：通过。
- 自动化测试：
  - `cargo test -p dsh-pager-grok-ui --no-default-features`：628 tests + doctest
    通过，0 failed；
  - `cargo test -p dsh-pager-bin`：11 unit + 14 integration tests 通过；
  - `python3 scripts/pty-stream-scroll.py --binary target/debug/dsh-pager`：通过，
    `top=235->234, down_reports=24, tail=34->69`。
- `ttyd 1.7.7 + xterm.js + Playwright 1.61.1/Chromium` 最终像素链路：
  - `NO_COLOR=1`，1200×800，证据
    `/tmp/dsh-chrome-browser-nocolor-clean-20260829-XBo8DS/`：浏览器错误为空；
    Turn Status 在 running 期间可见，UI 内部仍报告 `pane_animating=true` 和
    `animated_visible_lines>0`，但 xterm rail 采样在两帧都只有背景
    `(10,10,10)` 与终端前景 `(225,225,225)`，视觉上是静态白线；
  - 清除 `NO_COLOR`，1200×800，证据
    `/tmp/dsh-chrome-browser-color-20260829-Vyh7Wz/`：浏览器错误为空；同一 rail
    列在 Thinking A 帧含 `(44,44,44)/(58,58,58)/(70,70,70)/(80,80,80)`，
    Thinking B 帧变为 `(74,74,74)/(83,83,83)/(88,88,88)/(87,87,87)/
    (81,81,81)`，证明行波相位到达最终 xterm.js 像素；
  - 清除 `NO_COLOR`、`TERM_PROGRAM=vscode`、1074×650（约 116×33）并在流式期
    连续发送 8 次真实 `page.mouse.wheel(0, -120)`，证据
    `/tmp/dsh-chrome-browser-scroll-clean-20260829-prJGUC/`：7 个阶段截图完整、浏览器
    错误为空；`follow=true→false` 后 Turn Status 仍为 `visible=true`，且从
    `thinking` 正常转为 `responding`；只有 mock 最终发送
    `host/session-status running=false` 后才隐藏。
- 原因判定：
  - 已确认 reasoning rail “行波消失”的一个直接原因是父进程设置了
    `NO_COLOR`。crossterm 0.28.1 会在该变量非空时抑制颜色控制序列，因此动画状态
    和相位仍更新，但 xterm.js 只能画统一前景色；这不是滚动状态闭包删除动画；
  - 确定性协议、窄终端和真实鼠标滚动均未复现 Turn Status 在 running 中消失。
    当前代码中它随 `session.running/host session-status` 生命周期隐藏，而不随
    scroll follow 状态隐藏。因此真实 Harness 若在响应未结束时看不到该行，下一步应
    用本批日志核对是否收到过早的 `running=false`；在没有真实复现日志前不把该推断
    当作已确认根因；
  - 日志还显示 reasoning delta 当前会触发连续 `scrollback full-sync`。浏览器测试未
    发现它导致组件消失，但它可能是独立的流式卡顿成本，后续应单独做增量 sync
    profiling，不与本次可见性问题混为一谈。
