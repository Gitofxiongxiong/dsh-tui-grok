# DSH 多版本兼容架构方案

> 记录时间：2026-08-30 11:51:31 +0800
> 操作者/agent：Codex
> 状态：completed

## 目标与背景

- 当前 `main` 适配 DeepSeek Harness `0.1.2-alpha.1`，旧的
  `legacy/main-before-harness-0.1.2-alpha.1` 适配 `0.1.0-rc.8`；npm 最新可用
  DSH 为 `0.1.1-rc.2`。
- rc.8 与 rc.2 仍属于 Host ApiProxy/Remote API 架构族，alpha.1 已转向
  Controller、follow/control stream 与 waterfall 交互，是一次实质架构边界变化。
- 本批次仅写可评审的长期兼容方案，不改产品代码、依赖、profile、
  CI 或 npm 发布状态。

## 设计约束

- 一条产品主线，不为每个 DSH 版本长期复制整套 TUI 实现。
- Rust/Grok TUI 只消费项目自有的稳定 JSON-RPC 合同，DSH 变化限定在
  TypeScript adapter 和版本化 profile/runtime 边界。
- 必须区分“已发布 npm 依赖”与“仅源码 tag 可用”，不发布无法
  从 registry 安装的默认产品组合。
- 未在兼容矩阵中通过真实 E2E 的版本必须 fail closed，不根据宽泛 semver
  或方法是否存在静默猜测。

## 计划修改范围

- `docs/DSH_MULTI_VERSION_COMPATIBILITY_PLAN.md`
  - 写入现状证据、目标分层、`TuiBackend` SPI、adapter/profile/runtime 拆分、
    兼容矩阵、能力协商、测试与发布门禁、迁移阶段、风险、回滚与待决策项。
- `docs/开发进度记录/2026-08-30_11-51-31_DSH多版本兼容架构方案.md`
  - 记录本文档批次的范围、验证和提交信息。
- 不在范围内：TypeScript/Rust 产品源码、package manifest、lockfile、profile patch、
  shell script、GitHub Actions、npm publish、版本 tag 和 UI 视觉行为。

## 风险与回滚

- 风险：方案过度抽象会推高首次迁移成本；文档必须以现有 bridge 公开方法为
  SPI 起点，用分阶段无行为变化抽取降低风险。
- 风险：将 rc.8 与 rc.2 归为同一 adapter family 不等于未经验证的运行时
  兼容；只有公用 conformance suite 和真实 E2E 通过后才能进入 supported 状态。
- 回滚：本批次只新增两份 Markdown，可通过 revert 对应文档提交完整回滚，
  不影响当前 main 产品行为。

## 实际结果

- 新增 `docs/DSH_MULTI_VERSION_COMPATIBILITY_PLAN.md`，共 24 个编号章节，
  明确写出本次设计目的、实施后效果，以及两者逐项对应的可验证结果。
- 方案确定“一主线 + Rust canonical/TypeScript mirror 稳定协议 +
  `TuiBackend` SPI + adapter family + family-specific profile/runtime”的目标结构。
- 方案将 rc.8/rc.2 归入 `apiproxy-v1`，alpha.1 归入
  `controllers-v2`，但明确 rc.2 当前仅为 candidate，必须完成 conformance、
  real E2E、PTY 和 cold npm install 后才能改为 supported。
- 方案给出 support registry schema、capability 模型、CLI/doctor 行为、npm 与
  source-only 发布边界、分层测试矩阵、Phase 0–6 迁移步骤、逐阶段验收/回滚、
  风险与六个维护者决策项。
- 未修改 TypeScript/Rust 产品代码、manifest、lockfile、CI 或用户可见 TUI；
  因此本批次不运行产品测试或浏览器终端视觉对比。
