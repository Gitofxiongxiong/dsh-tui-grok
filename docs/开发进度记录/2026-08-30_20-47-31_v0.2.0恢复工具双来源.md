## 目标与背景

PR #9 与 main CI run `33311878749` 已全绿，本地也用 formal run 的
CLI artifact + registry native/runtime 完整通过 cold/doctor/smoke/PTY。但随后
recovery run `33312297700` 的 cold job 仍在旧 `realpathSync` 位置失败。

日志证明 workflow definition 确实来自 dispatch 时的
`main@980d5f980c8fcf349e4ded8fa8dafd662fcc3193`，但 cold job 按既有不可变
候选约束 checkout `v0.2.0@77ae309` 后，又从该 Tag 工作树执行了旧版
`scripts/rehearse-release-candidate.sh` 和 `scripts/audit-cold-install.mjs`。因此 PR #9
的已审核编排工具修复未进入 recovery job；候选 tarball/registry 内容没有
差异，CLI publish 与 final gate 依然跳过。

## 设计契约和复用依据

- 对应长期计划：`DSH_MULTI_VERSION_COMPATIBILITY_PLAN.md` §17.2、§19 Phase 6、
  §21.6；`GIT_PR_RELEASE_WORKFLOW.md` §7–§8。
- candidate source 与 release orchestration 必须分离：
  - package manifests、Tag 元数据、已保存 artifacts 与 registry integrity 仍只归
    `v0.2.0@77ae309` / source run `33309459911` 所有；
  - 为不重定位不可变 Tag 而修复纯编排故障，cold audit/rehearsal 工具只从
    本次 workflow definition 的精确 `${{ github.workflow_sha }}` 检出到独立目录。
- Tag checkout 仍保留在 cold job 根工作树；编排工具 checkout 不构建、
  重打或替换任何候选 tarball，只审计来源 run 的 CLI artifact 与 registry
  已发布包。
- Grok source path/commit/SOURCE_REV：不适用（发布编排修复，无 UI/源码
  变更）。
- 复用等级：D（发布工具，不进入 Grok UI 产品边界）。

## 计划修改范围

- `.github/workflows/release.yml`：cold job 保留 immutable Tag checkout，另将
  `${{ github.workflow_sha }}` 检出到 `release-orchestration/`，从后者执行
  rehearsal/audit。
- `docs/GIT_PR_RELEASE_WORKFLOW.md`：明确部分发布恢复时 candidate source
  与已审核 orchestration tools 的双来源边界。
- `docs/RELEASE_CANDIDATE_CHECKLIST.md`：追记 run `33312297700` 失败和下次
  recovery 要求。
- 本进度记录：回写实际修改、验证和后续。
- 不在范围：修改/force-push `v0.2.0` Tag，重打 package，覆盖已发布
  version，本批 commit 中执行 publish/dist-tag/Release。

## 风险、回滚和依赖

- 风险：编排 checkout 若使用浮动 `main` 而非 workflow definition SHA，重跑时可能
  引入未审核工具；必须精确锁定 `${{ github.workflow_sha }}` 并校验 checkout HEAD。
- 风险：工具 checkout 若被候选打包消费，会破坏 Tag 不可变性；cold job 只消费
  已下载 artifact/registry，不运行打包。
- 回滚：回滚本批单 commit 即恢复单 Tag 工作树；不影响 registry、Tag 或
  原 artifacts。
- 依赖：下次 recovery 仍必须使用 `resume_run_id=33309459911`，不得
  重建 Windows native。

## 实际修改

- metadata job 新增 `commit` output，把已解析的 immutable Tag commit 传给
  cold job，避免下游再次推断。
- registry cold job 仍先把根工作树 checkout 到 metadata Tag；然后把当前
  workflow definition 的精确 `${{ github.workflow_sha }}` 检出到
  `release-orchestration/`。
- cold job 在安装或演练前同时断言 root HEAD = metadata Tag commit、
  orchestration HEAD = workflow SHA；任一不一致即停止。
- cold rehearsal 改为执行
  `release-orchestration/scripts/rehearse-release-candidate.sh`。该脚本在 registry
  mode 只审计来源 run CLI artifact 与 registry native/runtime，不从 orchestration
  checkout build/pack 候选。
- 发布规范与 checklist 同步 candidate source/orchestration source 的所有权、
  commit 校验和第三次 recovery 失败事实。
