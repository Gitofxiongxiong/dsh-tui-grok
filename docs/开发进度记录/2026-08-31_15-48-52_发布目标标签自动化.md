# 发布目标标签自动化

> 记录时间：2026-08-31 15:48:52 +0800
> 操作者/agent：Codex
> 状态：completed

## 目标与背景

- 用户要求消除每次正式发布后为七个 npm package 逐项打开浏览器、完成 2FA 并执行
  `npm dist-tag add ... latest` 的重复操作。
- 当前 `release.yml` 已通过 npm Trusted Publishing/OIDC 安全发布 package，但全部先写入
  `release-candidate`；npm OIDC 只授权 `npm publish`/`npm stage publish`，不能用于
  `npm dist-tag`，因此现有流程必须在 workflow 外人工提升 `latest`。
- 本批改为让 stable 版本在经过既有 Tag、候选构建和顺序门禁后直接发布到 `latest`，
  prerelease 发布到 `next`；五个平台 native 和 runtime 先发布，CLI 继续最后发布。

## 设计契约和复用依据

- 保留 `docs/GIT_PR_RELEASE_WORKFLOW.md` 的两阶段契约：Tag push 只构建 immutable
  artifacts，只有默认分支的显式 `workflow_dispatch` 和
  `confirm=publish-vX.Y.Z` 才产生 registry 副作用。
- `metadata` 从经过校验的 Tag version 唯一计算目标标签：严格 `X.Y.Z` 为 `latest`，带
  prerelease suffix 的版本为 `next`；不接受可由 dispatch 任意指定的 tag，避免误把
  prerelease 提升为 stable。
- 发布顺序保持 native → runtime → official-registry cold/PTY（使用 CLI candidate）→
  CLI。旧 CLI 使用精确 native/runtime 依赖，不会因内部 package 的 `latest` 先移动而
  引用半发布版本；用户入口 CLI 的 `latest` 仍只在前置门禁全绿后改变。
- CLI publish 后必须再从 npm 官方源下载已发布 CLI，执行完整 cold/warm/offline、doctor、
  默认新建、显式恢复、迁移和 PTY rehearsal；通过后才自动创建 GitHub Release。
- recovery 继续只允许 immutable Tag commit 与来源 run 完全一致；已存在 version 必须校验
  tarball integrity 和目标 tag，绝不覆盖同版本。
- 不引入 `NPM_TOKEN`、granular bypass-2FA token 或 npm 网页设置变更；继续使用现有
  `release.yml`、`npm-release` environment 和 Trusted Publisher。

## 风险、回滚和依赖

- 风险：native/runtime 的目标 tag 会早于 CLI 改变。控制：它们不是公开入口，CLI 对其
  使用精确版本；CLI 仍最后发布，且此前已完成本地候选和官方 registry cold/PTY。
- 风险：CLI 发布后最终官方源 rehearsal 失败时 `latest` 已改变。控制：版本不可覆盖；
  workflow 停止且不创建 GitHub Release，维护者按事故流程显式回退 CLI tag 或发布新
  patch。Tag 前候选 rehearsal 和 CLI 前 registry rehearsal 已把该窗口压到最小。
- 风险：恢复 run 重复创建 Release。控制：Release job 先读取同 Tag Release；存在时只
  验证 draft/prerelease 状态，缺失时才创建。
- 风险：自动 Release 权限过宽。控制：仅最终 Release job 使用 `contents: write`；所有 npm
  job 继续最小 `contents: read` 与必要的 `id-token: write`。
- 回滚：在尚未执行新版本 dispatch 前可 revert 本批 commit；若新流程已部分发布，不移动
  immutable Tag 或覆盖版本，按记录的 recovery/新 patch 流程处理。
- 依赖：现有七包 Trusted Publisher 必须继续绑定 `release.yml` 和 `npm-release`
  environment，并允许 `npm publish`；本次不要求网页修改。

## 实际修改

- `.github/workflows/release.yml`
  - `metadata` 根据不可变版本输出 `target_tag`：严格 stable 为 `latest`，预发布为
    `next`。native、runtime 和 CLI 统一用 OIDC 直接发布到该目标 tag，恢复路径同时
    核对 tarball integrity 和目标 tag。
  - 保持 native → runtime → candidate registry rehearsal → CLI 的顺序；正式 CLI 入库后新增
    `registry-final` job，从 npm 官方源重新下载 CLI tarball 并运行完整发布演练。
  - 最终门禁通过后由独立 `github-release` job 幂等创建/验证 Release；stable 标记
    Latest，prerelease 标记 prerelease。仅该 job 具有 `contents: write`。
  - registry 核验加入短时重试以容忍 npm 复制延迟，并要求新版本具有 provenance。
- `scripts/release-workflow.test.mjs`
  - 新增 stable/prerelease 目标 tag、三类 publish 的 OIDC 参数、CLI-last 依赖链、最小权限、
    官方 CLI 复验和所有显式 Bash block 语法的自动化契约。
  - 显式禁止重新引入 `npm dist-tag`、`release-candidate` 发布参数、`NPM_TOKEN` 或
    `NODE_AUTH_TOKEN`。
- `package.json`
  - 将 workflow 契约测试纳入 `test:release-tools` 和现有 `verify:ts` 门禁。
- `docs/GIT_PR_RELEASE_WORKFLOW.md`
  - 更新目标 tag、两轮 registry rehearsal、CLI 最后发布、自动 Release、恢复及部分发布
    失败语义，并记录正常发布无需逐包浏览器 2FA。
- 未改动 package version、lockfile、产品代码、npm Trusted Publisher 网页配置和已发布版本。
