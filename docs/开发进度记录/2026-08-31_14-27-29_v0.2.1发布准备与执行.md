## 设计契约和复用依据

- 对应流程：`docs/GIT_PR_RELEASE_WORKFLOW.md` §7、
  `docs/RELEASE_CANDIDATE_CHECKLIST.md` 的 native → runtime → registry cold/PTY →
  CLI → registry verify → dist-tag → GitHub Release 顺序。
- 版本：Cargo workspace、根 npm manifest、全部 workspace package 和公开单元内部
  精确依赖同步为 `0.2.1`；DSH backend/runtime 仍固定 `0.1.1-rc.2`。
- 发布 source 必须是合入远端 `main` 的单一 commit 与 annotated `v0.2.1` Tag；Tag
  push 只构建 artifacts，待该 run 全绿后才从默认分支手动 dispatch
  `confirm=publish-v0.2.1`。
- 首次正式 run 不使用 `resume_run_id`。只有出现部分发布且候选内容不变的纯编排
  故障，才允许按流程恢复。
- 所有包先落在 `release-candidate`；七包 registry/provenance 和正式 cold/PTY
  全绿后，严格串行移动 `latest` 并创建 GitHub Release。

## 风险、回滚和依赖

- Tag 前失败：停止并修复 release branch，无 registry 副作用。
- Tag 后、publish 前失败：保留不可变 Tag，修复后发布新 patch；不重定位远端 Tag。
- 部分 package 已发布：不覆盖同版本；只有 artifact integrity 完全一致的纯编排故障
  才使用来源 run 恢复，否则停止并准备新 patch。
- `release-candidate` 仍指向旧版时不影响 stable 用户；`latest` 只在整条链全绿后移动。
- 发布 workflow 依赖 GitHub `npm-release` environment 和 npm Trusted Publisher；若
  出现浏览器/人工 environment approval，立即通知用户操作。
