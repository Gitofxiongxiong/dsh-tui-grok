# v0.2.0 正式发布工作流

> 记录时间：2026-08-30 18:39:13 +0800
> 操作者/agent：Codex
> 状态：completed

## 目标与背景

Phase 5–6 已合并到 `main`，commit `dafbe98f39d9a8a9dbabb234c5a12f2d5be81562`
的主分支 CI 全绿，维护者已明确批准发布 `0.2.0`。发布前复核发现当前
`.github/workflows/release.yml` 只构建原生 tarball，不执行仓库规范要求的
native → runtime → registry cold install → CLI Trusted Publishing 链路。

本批补齐正式 OIDC 发布工作流及其 registry cold-install 等价本地入口。新建包
`@dsh-pager-grok/runtime-apiproxy-v1` 因 npm Trusted Publishing 不能在包创建前配置，
允许由维护者已认证的本机从最终 Tag 做且只做一次 bootstrap publish；工作流必须对该
已存在版本做 tarball integrity 校验，后续版本仍走 OIDC。

## 设计契约和复用依据

- 对应规范：`docs/GIT_PR_RELEASE_WORKFLOW.md` §7.3–§7.6、
  `docs/RELEASE_CANDIDATE_CHECKLIST.md` §17.2 发布顺序与回退。
- Tag push 仍只构建并保存五平台原生/JS 候选 artifact；实际发布必须由维护者从同一
  Tag 手动 dispatch，并输入精确确认值。
- 发布包先使用隔离的 `release-candidate` dist-tag；全部 registry 验收通过后，维护者
  才移动 `latest`，避免部分发布污染稳定入口。
- 五个平台 native 和 CLI 使用 GitHub Actions OIDC；runtime 若版本不存在则使用 OIDC，
  若已由本次首包 bootstrap 创建，则必须与工作流从 Tag 重建的 tarball integrity 一致。
- registry cold install 复用现有 `rehearse-release-candidate.sh` 的完整
  doctor/hello/list/load/warm/offline/PTY 验收，仅参数化安装来源，不改变 TUI 或协议。
- Grok source/reuse：无 UI、wire 或 Grok vendor 变化，不适用 A0–D 复用分类。

  - 增加精确 registry version + CLI tarball 模式，保留原有本地候选模式。

  - 对齐正式 workflow 的真实触发、发布顺序、确认与 bootstrap 边界。

不在范围内：package/Cargo 版本、业务代码、Rust wire、协议版本、TUI 视觉、npm

## 风险、回滚和依赖

- OIDC trusted publisher 绑定 workflow 文件名、仓库和 environment；任一不符都应在
  首个 publish 步骤失败并停止后续 job。
- npm version 不可覆盖；每次发布前先查询精确版本。部分发布时停止，不重定位 Tag，
  不自动 unpublish，以新 patch 修复或 deprecate。
- registry 存在 runtime 版本时必须验证 SRI integrity；不一致立即失败，不发布 CLI。
- `release-candidate` 到 `latest` 的移动不放入 OIDC workflow，因为 npm OIDC 不授权任意
  dist-tag 操作；仅在全链验证后由已认证维护者显式执行。
- 回滚本批代码：revert 本批 commit；Tag 尚未创建时无 registry 副作用。

## 实际修改

- `.github/workflows/release.yml`
  - workflow 更名为 `release`；Tag push 只生成五平台 native 与 runtime/CLI artifact。
  - 手动 dispatch 必须从 Tag ref 运行并输入 `publish-vX.Y.Z`，同时校验 Tag 与八份
    product/public package manifest 的精确版本。
  - 五平台 native 使用 `npm@11.13.0` + `npm-release` environment OIDC 发布到
    `release-candidate`；runtime 在不存在时走 OIDC，已存在时校验 registry/local
    SHA-512 integrity；registry cold/PTY 通过后才发布 CLI。
  - 最终 job 核对七个公开包的精确版本、`release-candidate` tag，且除一次 bootstrap
    runtime 外均要求 provenance attestation。
- `scripts/rehearse-release-candidate.sh`
  - 保留无参数的本地 tarball 候选模式；新增
    `DSH_RELEASE_REGISTRY_VERSION` + `DSH_RELEASE_CLI_TARBALL` registry 模式。
  - registry 模式只从 Tag tarball 安装尚未发布的 CLI；native/runtime 必须从 npm
    registry 精确版本解析，并复用完整 doctor/hello/list/load/warm/offline/PTY 门禁。
- `docs/GIT_PR_RELEASE_WORKFLOW.md`、`docs/RELEASE_CANDIDATE_CHECKLIST.md`
  - 对齐两阶段 workflow、精确确认值、runtime 一次 bootstrap、隔离 dist-tag 和人工
    `latest`/Release 边界；登记维护者已经批准 `0.2.0` stable 发布。
